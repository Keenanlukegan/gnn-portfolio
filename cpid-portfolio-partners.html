Daily Automation Health Checker + Watchdog Mesh

Monitoring / Reliability
Live

A daily agent that audits every automation the business runs and writes one auditable health report, backstopped by deterministic watchdogs that alert the moment that report goes missing.

Problem → method

The business problem: automations fail silently (an app closes, an auth token expires, a write never syncs) and the gap can run for days before anyone notices. The method on show here is how he keeps a client's systems trustworthy long after launch: instead of trusting an automation to report its own health, he wraps a fallible AI audit inside a model-free watchdog that can't itself fail, with anti-false-positive rules so it only cries wolf when something is genuinely wrong, and it re-alerts his phone until a missing report is fixed. He assumes his own systems will break, and builds the thing that catches it when they do.

How it works
  • Daily 08:10 WITA the checker-agent runs a 12-step read-only audit: scheduled tasks (4 expected), Cowork skills, Apps Script health (Gmail + Executions cross-check), date-aware monthly maintenance, Gmail signals, memory, blueprint alignment, wiki health
  • Writes checker-agent/, then reads it back and verifies it has >50 lines (silent-write guard)
  • 09:00 WITA a launchd job path-scoped commits pushes the report to origin/main (the model never pushes itself)
  • 12:00 WITA a launchd job pings Telegram if today's report is missing from both local and origin/main or is <50 lines, and re-alerts on every fire until cleared
  • Anti-false-positive discipline is baked in: cross-check Gmail failures against the script's Executions tab, and reclassify any counter flagged 14+ days with no live signal as 'blocked not actionable'

CRM Autolog (WhatsApp -> CRM auto-ingest)

CRM
Live

Auto-ingests a business's unread customer chats into a structured CRM every few hours, then re-marks each chat unread so the follow-up queue is never lost.

Problem → method

The business problem: when inbound customer conversations never land in a structured CRM, leads and complaints slip through the cracks, and automating the capture introduced a subtler failure, because opening a chat to read it marked it read on the owner's phone and quietly emptied her follow-up queue for days. The method: he doesn't accept ‘it returned success’ as proof. He traced the silent break to a re-mark step that reported done without ever checking, then rebuilt it from a method that was failing almost every run into a verified one with an explicit check, a retry, and a log of every miss. He turns an invisible failure into an auditable one.

How it works
  • launchd fires the script every 4h; it acquires the shared WA-Web CDP lock for the entire scrape
  • findUnreadChats scans the WA Web chat list for [aria-label*=unread i] badges
  • For each unread chat it opens by exact name, extracts recent messages, computes direction (In/Out) and a replied flag (any later outgoing message after the inbound), and collects rows
  • Collected chats are POSTed (token-authed) to the CRM web app, which logs them and rebuilds the one-row-per-student Students view
  • reMarkUnread right-clicks the chat row -> 'Mark as unread' / 'Tandai belum dibaca', then verifies the unread badge returned (with one retry); failures are logged and written to.

Daily WhatsApp Class-Reminder Sender

Scheduling / Messaging
Live

An unattended daily sender that reminds every customer of their appointment: built defensively, because messaging apps lie about what they actually sent.

Problem → method

The business problem: appointment-based businesses bleed revenue to no-shows, so someone burns an hour every morning messaging customers by hand, and automate it naively and it quietly double-sends, or logs ‘sent’ for messages that never landed. How he found it: he refused to trust ‘message sent’, and re-reading the screen after every send surfaced that most of a batch logged as SENT had never actually delivered. How he solved it: phone-first opening so it can never message the wrong contact, three concentric dedup guards, and post-send verification that only logs SENT after confirming the message on screen, every rule earned from a real mis-send he caught. Find the silent failure, prove it, engineer it out: the method transfers to any business that messages its customers.

How it works
  • launchd fires the wrapper at 05:06 WITA Mon-Sat; a CDP preflight (, 10s) does a real connectOverCDP handshake and bails fast with a Telegram alert if Debug Chrome is wedged, rather than stalling on Playwright's 120s connect timeout.
  • Stage 1 commits pre-typed drafts (--send-drafts); stage 2 runs ONLY if the stage-1 JSON reports composeInvalid > 0 (the only failures a direct re-send can fix), both stages share a /tmp roster cache so a mid-run MASTER edit can't split the phone data.
  • Per student: open chat via web.whatsapp.com/send/?phone=62... (never name-search, which once mis-sent to a 'BUKTI PEMBAYARAN' chat), with up to 3 page.goto auto-retries and a name-search fallback for wrong/missing CONTACTS phones.
  • Three dedup guards before any send: SEND LOG sheet pre-filter, dual-anchor DOM check (today-dated bubble that contains BOTH 'pengingat otomatis' AND the student's full name), and an step for locale drift (Indonesian 'Kamis' vs 'Thursday').
  • After pressing Enter, polls the DOM for a new today-stamped reminder bubble before logging SENT; on timeout it logs FAILED, added after an audit found 23 of 40 logged-SENT messages never delivered.
  • Unread-badge preservation re-marks any chat that had an unread incoming customer message, so reminder sends don't silently empty the owner’s to-do queue; every outcome is appended to SEND LOG and the final summary is upserted into the CRM 'Reminder Daily' tab.

Art Journey Student Report Generator

Reporting
Shipped

Generates one polished, self-updating report per customer from scattered source data: produced in the hundreds, with zero failures.

Problem → method

The business problem: customers have no living view of their status, so staff field the same ‘where am I at?’ questions all day, and hand-built reports are stale the moment they're made. The method: he treats the platform's limits as adversaries to engineer around, not excuses: a merge-free layout to beat the runtime timeout, images embedded as values instead of fragile formulas that need a manual per-file grant, and reads from live sources instead of stale mirrors. How it works

  • A resumable Playwright CDP driver chunks the full batch and records done-IDs so a multi-hour run can stop and continue

Performance / Payroll
Shipped

Rebuilt performance-pay scoring after the business's only evaluation data source died and silently zeroed everyone's incentive pay.

Problem → method

The method: he root-caused the silent break, then re-architected scoring as a per-metric fallback dispatcher that reads each number from its true source, with a provenance stamp on every score so a broken pay tier is a one-glance debug instead of a mystery.   • Tier-pass rule gates pay: a teacher passes a weight tier only if ALL KPIs at that weight score >=80; missing data counts as failing

Legacy-to-Schedule-2026 Migration Tooling

Scheduling
Shipped

Migrated the live schedules that feed pay, KPIs and reminders off five mismatched legacy sheets, row by row, without corrupting a single record.

Problem → method

The business problem: the riskiest work in any business is changing the live system everything else depends on while it's still running. Do it carelessly and you corrupt the data that feeds payroll. The method: he did it incrementally and defensively, porting row by row, catching a validation-ordering bug and a wrong-event-type trigger (one set to ‘On open’ instead of ‘On change’) that a casual glance would ship, and using browser automation to reach places the normal tooling can't. What a partner is really evaluating is whether someone can move a live system without breaking it: this is the proof.

How it works
  • Two migration patterns: cross-sheet and same-sheet _2026 tabs, later consolidated into isolated per-teacher spreadsheets

  • Playwright over CDP renamed all 10 bound projects and installed onChangeBackup triggers, with a separate read-only verifier that counts rows and checks event type (caught a teacher’s 'On open' bug)
  • Bug-fix scripts repaired collateral damage: a teacher date fix re-anchored 25 date cells shifted ~105 days by a broken formula chain

Dynamic Roster Layout Discovery (REMINDER MASTER scanner)

Data integrity / Sheets
Live

A self-healing reader that re-discovers a spreadsheet's layout from its own headers every morning, so a staffer inserting a column at 4am doesn't break the 5am run.

Problem → method

The business problem: the moment a non-technical staffer edits the spreadsheet a script depends on, a naive automation silently reads the wrong columns and drops people: here it quietly served only part of the roster one morning. The method: he root-caused the layout regression and rebuilt the reader to re-learn the sheet's structure from its own headers at runtime, so it survives the humans editing it underneath. This is the line between a script that breaks the first time someone touches the sheet and one that just keeps running: the whole point of handing a client something that lasts.

How it works
  • Scan row 1 left-to-right; every non-empty cell whose value matches a teacher in JADWAL_SHEETS becomes that block's startCol; sort teachers by startCol.
  • For each teacher, scan row 3 from its startCol to the next teacher's startCol for the 'Day' header (hariCol) and the 'student'+'name' header (nameCol); timeCol = hariCol + 1 by convention.
  • Read data rows from row 5 to lastRow, filtering each block by the requested Day, and join to phones from the CONTACTS tab.
  • Explicitly avoids the older path that scanned row 2 for Indonesian 'hari' labels, row 2 is empty on the live sheet, so that path returned 0 for many day/teacher combinations.
